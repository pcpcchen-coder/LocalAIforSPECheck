# 驗收與真實模型評估

分開驗證「軟體流程正確」與「模型對真實規格判斷足夠可靠」。內建示範與模擬 API 的測試，不能代表任何本地模型的準確率。

## v0.3 完整工作流程驗收

下列是執行清單與通過條件，**不是聲稱已通過的結果**。實際執行平台、案例與數量見 [TEST_REPORT.md](TEST_REPORT.md) 及該次 Release 的測試報告。

| 編號 | 操作 | 通過標準 |
|---|---|---|
| V01 | 取得 Portable ZIP | ZIP 無任何 GGUF，但有 runtime、engine、下載器與模型說明 |
| V02 | 首次下載模型，再重跑下載器 | SHA-256／大小正確；第二次沿用原檔，不重新下載 |
| V03 | 離線匯入／同名錯誤模型 | `--source` 可驗證複製；錯誤同名檔保留、不覆蓋；自選模型不變 |
| V04 | 上傳兩份標準並抽取 | 原文、來源位置與獨立要求可查；無效引文或未處理文字留待處理項目 |
| V05 | 一段包含電壓及溫度，另有例外 | 可修改／拆成多項，條件與例外有來源；記錄前後版本與修改人 |
| V06 | 未抽取／未確認就建分析 | 拒絕開始，提示需處理的文件 |
| V07 | 第二份產品使用同一文件庫 | 已確認標準項目沿用；不重複呼叫抽取，新的分析另存快照 |
| V08 | 建立 300 份合成標準 | 文件清單可分頁查到全部；初篩每份都有紀錄，沒有 top-K 文件被靜默排除 |
| V09 | 模型判不適用或初篩出錯 | 文件仍預設保留；未知及錯誤明確顯示 |
| V10 | 排除標準 | 必須填理由與人員；保存選取歷史，匯出仍看得到被排除文件 |
| V11 | 聚焦模式找不到證據 | 擴大查核來源；覆蓋不足時不能標成完整符合或全文件未載明 |
| V12 | 高／未知關鍵性或待處理要求 | 掃描全部產品原文；未解析項目不消失 |
| V13 | 同一要求以全量模式處理 | 每個產品原文視窗均有處理紀錄；失敗視窗仍留疑義 |
| V14 | 產品缺少測試證據 | 標示證據缺口／待確認，不宣告產品物理失效 |
| V15 | 額定值與峰值、條件相異 | 不應僅因數值相同即視為同一要求；人工核對判讀及引文 |
| V16 | 覆核改判與調整風險 | 理由必填，原 AI 狀態保留，歷史可還原；版本衝突拒絕覆寫 |
| V17 | 取消／重啟／續跑 | 保存已完成工作，復原狀態正確，無重複結果與快照版本混用 |
| V18 | 查看未對應產品 | 排除任何標準時整體 coverage_complete 不得為真；已選範圍完整性另列，未解析項目仍顯示 |
| V19 | 三種匯出 | 含初篩、排除理由、差異、風險、待補證據、來源、抽取及覆核歷程；無 API key |
| V20 | 更新沿用舊 `data`、`models` | 舊 `/classic` 結果與歷史可讀；模型不需重抓；新版未偽造舊項目確認 |
| V21 | 從舊專案匯入產品與標準，再重複匯入 | 沿用原附件、SHA-256＋角色去重；原比對不變；新文件須抽取確認；缺附件拒絕匯入 |
| V22 | 關頁／重啟後找回抽取工作 | 文件列「查看進度」可讀取已保存工作，取消／續跑不另建重複結果 |

300 份合成文件可驗證資料量、分頁與遍歷完整性；若使用模擬模型，不測真實模型速度、語意準確率、CPU 記憶體峰值或真實標準適用性。不得把 V08 的成功作為企業文件庫品質已通過的證據。

### 真實文件的 v0.3 驗收方法

固定產品、標準版本與模型設定，由兩位領域人員先建立人工基準並協調歧異，分開標註：

1. 每份標準的相關性、適用性及理由，包括「資訊不足」。
2. 每個獨立要求的來源、條件、例外、測試方法及關鍵性。
3. 產品對應證據、預期符合狀態、風險覆核優先度與需補證據。
4. 人工排除文件的允許條件，以及應保留但被排除的錯誤。

| 指標 | 計算／觀察 | 試行通過條件 |
|---|---|---|
| 原子要求抽取召回 | 正確保留語意與條件的人工基準要求／全部人工要求 | 先定門檻；關鍵要求漏項逐一處理，不能用來源字元覆蓋率代替 |
| 相關標準召回 | 被判相關或保留待確認的人工相關標準／全部人工相關標準 | 建議初期 ≥95%，關鍵相關標準不得漏掉；同時報待確認比例 |
| 人工選取後召回 | 最後保留的人工適用／待確認標準／人工應保留標準 | 樣本內關鍵文件不被錯誤排除 |
| 差異召回 | 檢出的人工差異項／全部人工差異項 | 建議初期 ≥95%；同時報誤判與待確認，避免一律待確認看似通過 |
| 關鍵錯判符合 | 關鍵差異或缺證據被判為符合的數量 | 樣本內 0；不能外推未來零漏判 |
| 原文引文有效性 | 引文存在且引用型號／條件正確 | 字面有效與語意相關分別報告 |
| 風險覆核一致性 | 與人工的優先度一致程度及被降級的關鍵問題 | 門檻由工程／品質負責人設定；未知不算低風險 |
| 成本與效益 | 初次建庫、新產品分析、續跑、RAM 峰值及人工覆核工時 | 在實際辦公電腦量測，以可接受工時決定範圍 |

建議起始樣本至少 100–200 項代表要求，包含中英混合、單位換算、AND／OR、例外、跨章定義、表格、同名不同參數、缺證據及矛盾。正式擴到數百份標準時，增加不同類別與版本，保存人工基準及所有錯誤案例。

比較「直接把兩份文件交給同一模型」與本工具時，固定文件、模型、生成設定、人工答案與評估範圍；分別記錄漏判、錯判、來源品質及人工工時，不只比較輸出字數或總執行時間。

以下保留舊 `/classic` 流程的基礎驗收方式，與新版獨立項目評估不可混算。

## A. 可重現的自動測試

在虛擬環境執行：

```bash
python -m pip install -r requirements-dev.txt
python -m pytest
```

具體案例以 `tests/` 實際內容及執行輸出為準。任何未實跑的平台、模型或案例都不應標記已通過。

## B. 基本作業驗收

| 編號 | 操作 | 通過標準 |
|---|---|---|

| B09 | 完成一份多規範比對 | 每個規範區塊有結果；可以篩選差異與覆核狀態 |

| B11 | 各匯出 HTML／XLSX／JSON | 全部結果與未覆核項目保留；沒有 API key |
| B12 | 在匯出資料放入 HTML 標籤或 Excel 公式文字 | 作為文字保留，不能執行腳本／公式 |

## C. 覆核與恢復驗收

| 編號 | 操作 | 通過標準 |
|---|---|---|
| C01 | 確認 AI 判定 | 原 AI 判定保留，新增一筆具姓名、時間、版本的事件 |
| C02 | 更正並填寫理由 | 最終狀態改變；排序使用有效人工判定 |
| C03 | 空白理由更正 | 拒絕儲存並提示原因 |
| C04 | 填原因後重新開啟 | 回到待覆核、有效判定回到 AI 原值、歷史保留 |
| C05 | 同一列在兩頁籤從相同版本先後送出 | 第二次衝突得到 409／畫面提示，不能覆寫第一筆 |
| C06 | 查看覆核歷史並再匯出 | 依版本可還原確認→更正→重新開啟過程 |
| C07 | 比對中取消 | 等本次 HTTP 返回後停止；已完成列保留 |
| C08 | 取消後續跑 | 跳過已保存列，未完成列重新執行，不產生重複結果 |
| C09 | 比對中退出再重新開啟 | 上次工作標記中斷，可續跑；舊結果與覆核不遺失 |
| C10 | 修改模型設定後續跑舊比對 | 使用原 Run 的模型與參數快照；換模型須另建比對 |
| C11 | 移除產品、上傳新版並重新比對 | 舊 Run 的文件快照、結果及原檔仍可追溯 |
| C12 | 停止程式，備份並還原整個資料目錄 | 專案、原檔、結果、設定及覆核歷史完整恢復 |
| C13 | 匯出，修改覆核，再匯出一次 | 留下兩份紀錄與各自 SHA-256；重新下載第一份仍與初次位元組完全相同 |
| C14 | 查看 Run 來源快照 | 可找到模型參數、文件雜湊、提示詞版本與雜湊 |

## D. 真實模型上線前驗收

選擇至少一份可對外使用的代表性產品文件，以及兩份與實際工作難度相近的規範。由兩名熟悉產品的工程師先建立人工基準，意見不同先協調確認，避免拿未審核的 AI 結果當標準答案。

人工基準至少涵蓋下列情境：

- 數值相同、數值不同、上下限與容許公差。
- 單位等價及換算，如 `0.1 kV` 與 `100 V`。
- 包含／未包含範圍，如工作溫度要求與產品額定區間。
- 必須符合的多個條件，其中只有一項不符合。
- `and`／`or`／除外條件／僅在特定模式適用。
- 數值在表格、證據在後文、或產品不同段落存在矛盾。
- 要求未載明與確實不符合的區別。
- 圖片／掃描／公式／註腳中存在重要條件，純文字不完整。
- 型號、測試條件、版本與引用標準不同。

建議基準至少 50 個人工拆分的原子條件，保留每項來源位置、預期狀態、產品證據與關鍵性。這是起始驗收規模，不足以推估所有文件的表現。

| 指標 | 算法／記錄內容 | 建議起始門檻 |
|---|---|---|
| 結構處理覆蓋 | 有結果的規範區塊／全部規範區塊 | 100%；模型失敗須仍保留待確認列 |
| 原文證據可追溯 | 可在引用位置核對的引述／全部引述 | 100%；不符者不能維持肯定判定 |
| 原子差異召回率 | AI 找出的人工已知差異／人工基準全部差異 | 先以 ≥95% 作試用門檻，依風險提高 |
| 關鍵差異漏判 | 關鍵差異被判為符合或未提示 | 此驗收樣本內 0 件；不能外推為未來零漏判 |
| 狀態一致率 | 與人工基準一致的項目／可對應項目 | 記錄各類混淆，門檻由品質負責人設定 |
| 待確認比例 | 待確認項目／全部結果 | 記錄原因，不能為降低比例而強行改成符合 |
| 處理成本 | 總耗時、模型呼叫數、RAM／GPU 峰值 | 依同仁可接受工時與硬體設定 |
| 人工覆核時間 | 每份文件人工基準工時與工具輔助工時 | 實測，再決定是否擴大使用 |

規範一個區塊含多個原子條件時，評估召回率須由人工逐條對應，不能直接用程式的區塊數代替。不同模型、量化版本、context 長度、提示詞或服務版本改動後，應重跑代表性樣本。
