# 用人工標準答案驗收模型

v0.3.3 新增獨立的[本機原子萃取探針與品質指南](LOCAL_EXTRACTION_QUALITY.md)，可直接呼叫本機模型跑合成案例；不是下列舊版比對腳本，也不等同真實文件的獨立人工驗收。

**版本範圍：本頁現有 `scripts/evaluate_gold.py` 與三列範例是 `/classic` 的區塊層級評估工具。** v0.3 同一原文區塊可拆出多個項目，不能把 item ID／block ID 隨意替換後套用舊答案；重複來源可能會被舊腳本視為重複鍵。

新版請依 [v0.3 驗收方法](ACCEPTANCE.md#真實文件的-v03-驗收方法) 保存獨立項目、標準初篩及人工選取基準，使用匯出的項目與來源快照逐項對照。相關性召回、適用性、原子抽取完整性、風險優先度與人工排除錯誤，尚不是下列舊腳本自動計算的指標。

下列內容保留供既有工作與歷史評估重現。

`scripts/evaluate_gold.py` 會讀取本工具匯出的 JSON 與獨立人工標註，輸出可重複計算的評估報告。它只使用 Python 標準函式庫，不呼叫模型、不改寫匯出、不變更人工覆核紀錄。

**評估只使用 `results[].status`，不使用 `review.final_status`。**這樣即使同仁已把錯誤判定改正，也不會將人工更正後的結果當成 AI 成績。這裡的 AI 判定指應用程式保存、經引用驗證等處理後的原始結果，不是未經處理的模型逐字輸出。

## 1. 操作步驟

1. 選用固定版本的產品文件及規範文件，在抽取預覽確認內容與區塊 ID。
2. 由領域同仁先建立標準答案。建議兩位同仁獨立判讀，再討論歧異；不要直接抄模型的判定作為答案。
3. 使用 **Local／本地模型模式** 完成比對，匯出 JSON。示範模式沒有呼叫模型，只能測操作與評估流程。
4. 建立人工答案 JSON，執行下列命令。
5. 檢查警告、缺少預測、錯判符合、關鍵條件錯判及引用，再看整體比例。
6. 修正文件解析、prompt、模型或設定後，以相同文件與答案重新執行，保留每次報告。

Windows 在專案目錄開啟終端機：

```powershell
.venv\Scripts\python.exe scripts\evaluate_gold.py reports\run.json reports\gold.json --output reports\evaluation.json
```

macOS／Linux：

```bash
.venv/bin/python scripts/evaluate_gold.py reports/run.json reports/gold.json --output reports/evaluation.json
```

也可用已安裝的 Python 3.11 以上版本取代虛擬環境 Python。不加 `--output` 會將 JSON 印到終端機；使用 `--output` 會建立必要資料夾，並寫入指定檔案。不要將正式產品文件、匯出或人工答案提交到公開 GitHub。

Exit code `0` 表示報告產生成功，**不代表模型通過驗收**。輸入不合法或檔案讀寫失敗回傳 `2`。此腳本沒有自動核准或 `--strict` 門檻；通過條件由團隊事先訂定。

## 2. 人工標準答案格式

人工答案的頂層包含 `rows`，每列使用規範檔名與區塊 ID 作為唯一鍵：

```json
{
  "rows": [
    {
      "standard_name": "standard_a_48v.txt",
      "block_id": "B00001",
      "status": "match",
      "critical": true
    }
  ]
}
```

| 欄位 | 填寫方式 |
|---|---|
| `standard_name` | 與匯出中的規範檔名完全相同，包含副檔名；大小寫亦須一致 |
| `block_id` | 規範區塊 ID，例如 `B00001`；不要填成產品證據區塊 ID |
| `status` | 下表其中一個英文代碼 |
| `critical` | 明確填 JSON 布林值 `true` 或 `false`，不能填字串 `"false"` |

| 代碼 | 人工標註意義 |
|---|---|
| `match` | 所有要求有足夠產品文件證據且相符 |
| `partial` | 複合要求只有部分相符，仍有差異或缺漏 |
| `mismatch` | 有直接證據顯示要求不相符 |
| `missing` | 產品文件沒有提供該項證據；不是宣告實體產品不合格 |
| `uncertain` | 文件歧義、適用條件或證據不足，無法可靠分類 |

`critical` 應由工程／品質同仁依需求重要性事先標註。缺列、重複的 `(standard_name, block_id)`、不合法狀態及非布林 critical 都不應被默默忽略。腳本會拒絕不合法答案、答案或預測中的重複比對鍵，以及 JSON 物件內的重複欄位。

同一 run 若有兩份規範檔案同名且區塊 ID 相同，這個答案格式無法區分；請在上傳前使用不同檔名並重跑，不要任意刪除一份結果。

### 隨附三列模板

`examples/gold_template.json` 對應 `examples/product_48v_controller.txt` 與 `examples/standard_a_48v.txt`：

| 規範區塊 | 範例人工答案 | 理由 |
|---|---|---|
| `B00001` 額定電壓 48 V | `match` | 產品額定電壓亦為 48 V |
| `B00003` 工作溫度 -30 至 70 °C | `mismatch` | 產品僅聲明 -20 至 60 °C，無法涵蓋所需完整範圍 |
| `B00004` 防護等級 IP54 | `missing` | 產品文件未提供防護等級 |

請以原檔名上傳這兩個範例，使用 Local 模式執行並匯出，再將此模板作為第二個輸入。模板刻意只有三列，未標註的通訊介面列會被列為 `unscored_predictions`；它只能示範計算方法，不能作為正式驗收資料集或模型實測成績。增加／刪除文件行或重新命名後，先核對區塊 ID 再使用。

## 3. 評估數字怎麼解讀

所有 rate 都是 **0–1 的比例**，例如 `0.95` 表示 95%。`null` 代表無法計算，不代表 0%，也不代表通過。

令差異類別為 `{partial, mismatch, missing}`，需覆核類別為上述三類加上 `uncertain`：

| 欄位 | 計算與意義 |
|---|---|
| `metrics.prediction_coverage` | 對得上的人工答案列數 ÷ 全部人工答案列數 |
| `metrics.accuracy` | AI 狀態與人工答案完全相同的列數 ÷ 全部人工答案列數 |
| `metrics.difference_recall` | 人工為差異類別、AI 亦判成任一差異類別的列數 ÷ 人工差異列數 |
| `metrics.review_detection_rate` | 人工為需覆核類別、AI 亦判成任一需覆核類別的列數 ÷ 人工需覆核列數 |
| `metrics.difference_review_capture_rate` | 人工為差異類別、AI 判為差異或待釐清的列數 ÷ 人工差異列數 |
| `counts.false_match_count` | AI 判 `match`，但人工答案不是 `match` 的數量；包含人工答案為 `uncertain` |
| `counts.critical_false_match_count` | 上述錯判符合中，人工另標 `critical=true` 的數量 |
| `counts.missing_predictions` | 人工答案有標註，但執行匯出沒有對應列的數量 |
| `counts.unscored_predictions` | 匯出有結果，但人工答案未標註的列數 |

例如人工標 `mismatch`，AI 標 `partial`：完整分類算錯，但已檢出差異。若 AI 標 `uncertain`，差異召回不加分，送交覆核的檢出率會加分。把所有列都標待釐清，可能得到很高的覆核檢出率，因此**不可單看這個數字**；應同時看 accuracy、差異召回與混淆矩陣。

只要至少一列答案能對上，缺少的預測仍保留在品質比率分母中，不會被刪掉使分數變高。若完全對不上，品質比率回傳 `null` 並警告，覆蓋率為 0；人工答案為空時覆蓋率也是 `null`。某類別分母為 0 時，其比例為 `null`。

`confusion_matrix` 的第一層為人工真值、第二層為 AI 狀態，值是列數。`__missing_prediction__` 表示沒有對應預測，不同於語意分類 `missing`。報告亦含逐列答案、AI 狀態與錯誤，方便定位。

### 引用有效率

`citations.quote_validity_rate` 評估匯出中**所有結果列**的引文，而非僅人工答案子集。腳本確認每段非空引文存在於它指向的產品區塊，僅將空白字元正規化；改寫、翻譯或引用不存在的 block ID 不算有效。

- 分母為實際匯出的引文數，沒有引文時回傳 `null`。
- `rows_without_valid_required_evidence` 顯示 `match`／`partial`／`mismatch` 列缺少有效證據的數量，避免完全不引用卻被誤認為良好。
- 引用存在不代表語意相關，也不代表條件和適用範圍正確。
- 引文來源是匯出內的文字快照，無法據此證明 PDF/OCR 抽取無誤；仍需人工檢查原文件。
- 推論時被本工具移除的無效引文不會出現在匯出，因此此數值是**已保留引文的有效率**，不是模型最初輸出的幻覺率。

## 4. 正式驗收與限制

請固定文件版本，保存原檔 SHA256、模型 ID、量化、引擎版本、設定、run JSON、人工答案與評估報告。腳本依檔名和區塊 ID 對應；它不會自動證明答案與原檔 SHA256 相符，因此換文件版本後應重新核對／標註。

可參考以下試行門檻，由負責人先確認適用性：

- 至少 100–200 條代表要求，涵蓋中英混合、單位換算、限值、例外、跨章條件及缺證據。
- 人工答案範圍內的預測覆蓋率 100%；缺列應先處理。
- 差異列召回率至少 95%；所有已標註關鍵條件的錯判符合數為 0。
- 對全部錯判符合、待釐清及無有效證據的列逐一確認。

這是**區塊層級的分類評估**，不是區塊內每個原子差異的完整召回率，也無法偵測抽取時根本未進入答案集的遺漏。正式驗收仍需檢查每列所有子條件與抽取完整性。關鍵錯判數為 0，只表示此樣本未發現，不表示任意新文件都不會發生。

示範模式與未完成執行會在報告 `warnings` 明示；即使計算出 100%，也不能將示範結果或過小樣本當成模型能力證明。CLI 不會自動宣告驗收通過。
